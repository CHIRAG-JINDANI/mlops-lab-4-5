\begin{abstract}
Reproducibility and auditability in production machine learning systems require coordinated versioning across source code, dataset distributions, and serialized model artifacts. This laboratory report investigates the core engineering challenge: \textit{Can another engineer identify the model that was deployed and recover the exact code and dataset version used to create it?} By establishing an integrated MLOps architecture leveraging \textbf{Git} (code and metadata), \textbf{DVC} (content-addressable dataset storage and pipelines), and \textbf{MLflow} (tracking, model signatures, and model registry lifecycle governance), we demonstrate full bidirectional lineage tracking for a California Housing price prediction system across multiple candidate models, dataset revisions, and promotion states.
\end{abstract}

\section{Introduction \& System Architecture}
In conventional software engineering, Git snapshots the entire runtime state. In machine learning, code alone is insufficient because models are downstream artifacts of non-deterministic optimization over external data distributions. 

The tri-pillar MLOps architecture implemented in this work resolves this challenge by dividing responsibilities cleanly:
\begin{enumerate}
    \item \textbf{Git}: Tracks source code (`src/`), hyperparameters (`configs/config.yaml`), and lightweight metadata pointers (`.dvc`, `dvc.yaml`, `dvc.lock`).
    \item \textbf{DVC}: Tracks high-volume dataset payloads (`data/dataset.csv`), caching binary content in an external remote storage (`../dvc-storage`) indexed by cryptographic MD5 content hashes.
    \item \textbf{MLflow}: Tracks experiment runs, logs metrics ($MAE, RMSE, R^2$), visual diagnostic plots, model signatures, and manages operational lifecycle states (`@production`, `@candidate`, `@archived`) in a centralized Model Registry.
\end{enumerate}

\section{Part A: Advanced MLflow (Lab 4)}

\subsection{A1. Theoretical Research \& Core Concepts}
\begin{itemize}
    \item \textbf{Model Signature}: A formal specification defining the expected schema of model inputs and outputs, including column names, primitive data types (e.g., \texttt{double}, \texttt{integer}), and dimensional shapes (scalars or tensors). It enables early schema validation during model serving, catching malformed inference requests before execution reaches internal estimator code.
    \item \textbf{Artifacts}: Files produced during a run that provide model weights, runtime configurations, or evaluation diagnostics (e.g., \texttt{residuals\_plot.png}, serialized weights \texttt{model.pkl}, environment specifications \texttt{requirements.txt}, and evaluation reports \texttt{evaluation\_report.json}).
    \item \textbf{Autologging}: Framework-level introspection utilities (e.g., \texttt{mlflow.sklearn.autolog()}) that automatically intercept training loops to record hyperparameters, execution times, and standard metrics. Empirical verification showed it captured standard estimator parameters, but custom operational metrics (DVC hashes, Git commit SHAs, and specific test splits) required hybrid explicit logging.
    \item \textbf{Model Registry}: A centralized database-backed catalog managing registered model names, versions, metadata, and lifecycle stages. It decouples client-facing serving endpoints from ephemeral run identifiers.
    \item \textbf{Version vs. Stage / Alias}: A \textit{version} is an immutable, monotonically increasing integer identifying a specific checkpoint. A \textit{stage/alias} is a mutable semantic pointer (e.g., \texttt{@production}, \texttt{@candidate}) communicating current operational readiness.
\end{itemize}

\paragraph{Discussion on Schema Enforcement:}
If a downstream API client supplies only 3 columns or alters a numeric column to a string, MLflow's pyfunc serving handler intercepts the request and throws an HTTP 400 Bad Request error specifying the exact missing/invalid feature. While signatures detect structural and type violations, they \textit{cannot guarantee} protection against semantic anomalies, such as out-of-distribution values (e.g., negative house age), coordinate drift, or data poisoning within valid numerical bounds.

\paragraph{Critical Thinking: Should the highest-accuracy model always be promoted?}
No. Solely relying on aggregate RMSE or accuracy introduces substantial risks:
\begin{enumerate}
    \item \textbf{Latency \& Resource Footprint}: Deep ensembles may incur high p99 inference latencies, violating real-time production SLAs.
    \item \textbf{Subgroup Fairness}: Aggregate accuracy can mask severe prediction errors on disadvantaged demographic or geographic subsets.
    \item \textbf{Robustness \& Overfitting}: Complex models may overfit specific test splits, degrading rapidly under production distribution shifts.
    \item \textbf{Asymmetric Error Costs}: Severe underestimations in housing appraisal carry different legal and financial liabilities than overestimations.
\end{enumerate}

\section{Part B: Data Versioning with DVC (Lab 5)}

\subsection{B1. Data Versioning Principles}
Git stores complete delta snapshots in `.git/objects`, causing massive repository bloat when managing binary data or large CSV files. DVC solves this by storing only small ASCII pointer files (`.dvc`) in Git, while moving raw data to content-addressable storage indexed by MD5 hashes.

\subsection{B5 \& B6. Dataset Version Evolution and Recovery Verification}
Two dataset versions were tracked and verified:
\begin{itemize}
    \item \textbf{Dataset v1 (Baseline)}: 20,640 records (1,895,154 bytes, MD5: \texttt{ca5b757f0729c68d74d05bf9d9ca8486}). Committed to Git at \texttt{6767005}.
    \item \textbf{Dataset v2 (Evolution)}: 20,740 records (1,903,729 bytes, MD5: \texttt{5968e75c88d31ad1a1083b00d57fba4e}) containing 100 new survey samples. Committed to Git at \texttt{666c6cd}.
\end{itemize}

\paragraph{Verification Methodology:}
Restoration was verified by checking Git commit \texttt{6767005} on a verification branch, running \texttt{dvc checkout}, and executing line count checks (\texttt{wc -l}) and MD5 checksum comparisons. A filename alone (e.g., \texttt{dataset.csv}) is insufficient to identify a dataset version because file contents can mutate silently without the filename changing; only cryptographic content hashes guarantee immutability.

\subsection{B7. Reproducible DVC Pipelines}
A multi-stage pipeline was declared in \texttt{dvc.yaml} linking \texttt{data/dataset.csv.dvc} to \texttt{train\_and\_evaluate}. Running \texttt{dvc repro} generates \texttt{dvc.lock}. Subsequent runs skip execution if dependencies and code are unchanged, guaranteeing efficient computational reproducibility.

\subsection{C2. Anomaly Investigation \& Prediction Lineage Walkthrough}
When an anomalous prediction is flagged in production:
\begin{enumerate}
    \item \textbf{Identify Production Model}: Query MLflow for \texttt{models:/HousePriceModel@production}, returning Version 3 (Run ID \texttt{d5f0fe90}).
    \item \textbf{Inspect Audit Tags}: Extract \texttt{git\_commit\_sha} (\texttt{666c6cd8}) and \texttt{dvc\_dataset\_hash} (\texttt{5968e75c}).
    \item \textbf{Reconstitute Code}: Execute \texttt{git checkout 666c6cd8}.
    \item \textbf{Reconstitute Data}: Execute \texttt{dvc checkout}, instantly restoring the exact 20,740 rows used for training.
    \item \textbf{Reproduce & Debug}: Evaluate predictions locally, reproducing the exact weights, features, and environment without discrepancy.
\end{enumerate}

\section{Conclusion}
This assignment demonstrates that full reproducibility in modern machine learning systems requires strict decoupling and synchronization across source code, dataset snapshots, and model lifecycle metadata. By binding Git commit hashes and DVC content checksums directly into MLflow Model Registry tags, ML engineering teams achieve complete traceability, streamlined rollback mechanisms, and robust production governance.
